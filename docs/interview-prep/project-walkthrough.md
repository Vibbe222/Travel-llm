# 旅游规划机器人项目讲稿

## 1. 2-3 分钟项目介绍

这个项目是一个基于 LangGraph 的旅游规划机器人，目标是把大模型能力和多个外部工具串起来，帮用户生成更完整的旅游方案，而不是只返回一段泛化建议。

从技术结构上看，它的主链路是：前端或 Gradio 收到用户问题后，把消息交给 `chat_service.py`，再进入 `graph/graph.py` 里定义的 LangGraph 工作流。图里核心有两个节点，一个是负责决策的 Agent，一个是负责执行外部能力的 ToolNode。Agent 根据当前消息判断要不要调用工具，如果要，就进入工具节点执行；工具结果再回到 Agent，由 Agent 继续决定是继续查信息还是直接生成最终回答。

模型层在 `models/qwen_factory.py`，当前不是直接调 OpenAI，而是通过 DashScope 的 OpenAI 兼容接口去调用 `deepseek-v4-flash`，这样可以复用 LangChain 现成的 `ChatOpenAI` 接口。状态层很轻，只在 `states/state.py` 里维护 `messages`，再通过 `InMemorySaver` 做会话级记忆，适合演示，但不适合生产。

对外入口有两个。一个是 `webrun.py`，提供 Gradio 界面，适合本地演示和调试；另一个是 `api/main.py`，提供 FastAPI 接口和 NDJSON 流式输出，前端页面在 `templates/index.html`，会把模型流式 token 和工具调用过程实时展示出来。

工具层是这个项目的核心价值来源，包括 DuckDuckGo 网页搜索、高德地图坐标查询、高德周边 POI、高德公交路线规划，以及 Selenium 抓取马蜂窝景点信息。整体上，这个项目体现的不是单次问答，而是一个“模型做决策、工具补信息、图负责编排、前端流式消费结果”的 Agent 应用闭环。













这个项目怎么描述前端是怎么做的

这个项目的前端可以概括成一句话：

它不是重前端业务系统，而是一个“用于消费后端流式 Agent 结果的轻量单页界面”，核心价值在于把模型输出和工具调用过程可视化。

你面试里可以这样描述：

这个项目前端主要有两套入口。早期是 webrun.py 里的 Gradio 界面，适合快速原型和调试；后面又补了一套更接近真实服务化的前后端分离实现，在 api/main.py 提供接口，在 templates/index.html 用 Vue 3 写了一个单页前端。这个页面负责三件事：创建会话、发送用户消息、流式接收后端返回的 NDJSON 事件。

如果面试官继续追问“具体怎么做的”，你可以顺着讲：

前端没有做复杂工程化，而是直接在一个 HTML 文件里通过 CDN 引入 Vue 3、marked 和 DOMPurify。Vue 负责状态管理和交互，marked 把助手返回的 Markdown 转成 HTML，DOMPurify 做安全清洗。页面结构上分成两块：左边是聊天区，右边是工具调试面板。聊天区展示用户消息和助手回复，调试面板展示 tool_start 和 tool_end 事件，这样用户不仅能看最终答案，也能看到 Agent 中间调用了哪些工具。

再细一点可以说交互链路：

前端加载后会先调用 POST /sessions 创建 thread_id；用户发送消息时调用 POST /chat/stream；后端返回的是流式 NDJSON，前端通过 response.body.getReader() 持续读取数据，再按行解析 JSON。解析后如果是 chunk，就把内容不断追加到当前助手消息；如果是 tool_start 或 tool_end，就写到右侧调试面板。所以它的重点不是炫技 UI，而是把“模型流式输出 + 工具执行过程”实时展示出来。

你还可以补一句设计评价：

这个前端实现比较轻，优点是开发成本低、非常适合 Agent demo 和链路验证；缺点是没有做复杂状态管理、鉴权、持久化和异常恢复，更像演示型前端，而不是完整生产前端。

## 2. 主链路怎么讲

面试官如果让你从用户发一句话开始讲，建议按下面这条顺序：

1. 用户在 Gradio 或前端页面输入旅游需求。
2. `webrun.py` 或 `api/main.py` 接收请求，创建或复用 `thread_id`。
3. `chat_service.py` 调 `get_app()` 懒加载 LangGraph 应用，并构造 config。
4. `iter_chat_events()` 调用 `app.astream_events(...)` 开始跑图。
5. 图从 `START` 进入 `agent` 节点，Agent 用 prompt + 历史消息调用模型。
6. 如果模型返回 tool calls，`tools_condition` 把流程路由到 `ToolNode`。
7. ToolNode 执行对应工具，比如搜索、坐标、路线或景点抓取。
8. 工具结果写回消息流，再回到 `agent` 节点继续推理。
9. 当模型不再发出 tool calls，而是直接输出内容时，图结束。
10. `chat_service.py` 把 LangGraph 事件标准化成 `chunk`、`tool_start`、`tool_end`、`done`。
11. Gradio 或 FastAPI 前端按流式事件实时渲染回答和调试面板。

一句话总结这条链路：

> 这个项目不是“模型直接回答”，而是“模型先决定要查什么，再由工具查，再回到模型综合生成答案”。

## 3. 按模块拆解

### `chat_service.py`

职责：

- 创建会话和 `thread_id`
- 构造 LangGraph 的 config
- 把底层事件统一包装成前端可消费流

为什么这样做：

- 把图执行逻辑和界面层解耦
- Gradio 和 FastAPI 都能复用同一套流式服务层
- 统一处理事件格式，前端更简单

风险和限制：

- `thread_id` 基于时间字符串生成，唯一性和可追踪性一般
- 只做了轻量事件标准化，没有更细的 tracing
- 失败时主要返回错误文本，没有分级错误码

### `graph/graph.py`

职责：

- 定义整个 LangGraph 工作流
- 把 Agent 和 ToolNode 串成循环
- 通过 `tools_condition` 控制是否继续调用工具

为什么这样做：

- 旅游规划天然是多步任务，不适合一次 function call 解决
- 需要“查信息 -> 反思 -> 再查 -> 最终汇总”的循环
- LangGraph 比简单链式调用更适合带状态的多轮工具编排

风险和限制：

- 当前图结构比较简单，只有一个 Agent 和一个 ToolNode
- 缺少更细粒度节点，比如独立的规划、校验、总结节点
- 复杂逻辑主要压在 prompt 中，可维护性一般

### `agents/agents.py`

职责：

- 初始化模型
- 把工具绑定到模型
- 组装 prompt 并发起模型调用

为什么这样做：

- 将模型工厂和业务图逻辑分开
- 支持同步和异步 Agent 两种模式
- 首条用户消息被嵌入 prompt，规避部分模型对 system prompt 支持不稳定的问题

风险和限制：

- prompt 很重，很多业务规则依赖模型遵守
- 缺少更明确的结构化输出约束
- 工具选择正确性高度依赖模型理解能力

### `models/qwen_factory.py`

职责：

- 封装模型初始化
- 读取 `DASHSCOPE_API_KEY`
- 使用 OpenAI 兼容接口创建 LangChain chat model

为什么这样做：

- 上层代码只关心 `get_llm()`，不关心底层提供商
- 兼容 LangChain 的工具绑定和流式能力

风险和限制：

- 模型名和 base URL 写死在工厂里，灵活性一般
- 对配置校验比较少
- 没有为超时、重试、熔断做统一封装

### `states/state.py`

职责：

- 定义图状态结构
- 当前只存 `messages`

为什么这样做：

- 最简状态设计，便于接入 LangGraph 消息累加能力
- 对 demo 来说实现成本低

风险和限制：

- 缺少结构化中间状态，比如已选景点、已查路线、候选城市
- 一旦流程变复杂，全部靠消息上下文会越来越脆弱
- 不利于可观测性和精确恢复

### `api/main.py` 和 `templates/index.html`

职责：

- FastAPI 提供会话创建和流式聊天接口
- Vue 页面消费 NDJSON 流并展示调试信息

为什么这样做：

- 演示了 Agent 应用从后端到前端的完整流式链路
- 比纯 Gradio 更接近前后端分离的真实服务

风险和限制：

- 页面是轻量 demo，缺少鉴权、会话管理和持久化
- 流式协议简单直接，但没有更完整的错误恢复机制
- 文本里能看到编码历史痕迹，说明文档和模板编码需要统一治理

### `tools/*.py`

职责：

- `web_search.py`: DuckDuckGo 搜索
- `locations.py`: 高德地理编码
- `nearby.py`: 高德周边 POI
- `transportation.py`: 高德公交路线规划
- `attractions.py`: Selenium + 马蜂窝景点抓取
- `save.py`: 保存中间有用信息

为什么这样做：

- 让模型不只靠参数化知识，而是能拿到更实时、更具体的信息
- 不同工具各自对应旅游规划中的一个子问题

风险和限制：

- 返回结构不完全统一
- 异常处理风格不统一，有的返回错误对象，有的直接抛异常
- Selenium 和页面抓取非常依赖外部环境与 DOM 稳定性

## 4. 必答八股怎么和项目绑定

### LangChain 和 LangGraph 的区别

可以这么答：

LangChain 更像组件库，提供模型、提示词、工具、输出解析等基础能力；LangGraph 更适合把这些组件组织成带状态的工作流。这个项目里，工具绑定和模型调用能力来自 LangChain，而“Agent 和工具之间循环执行”的工作流由 LangGraph 管。

### 为什么这里要用 Graph，而不是单次 function call

因为旅游规划不是一步拿结果的任务。模型通常要先判断目的地是否明确，不明确就先搜索；确定目的地后还要抓景点、查经纬度、查路线，再回到模型综合。这个过程天然是多步循环，用 Graph 更容易表达。

### Tool calling 的机制是什么

模型在绑定工具后，会在回复中返回结构化 tool calls。LangGraph 的 `tools_condition` 会检查最后一条 AI 消息里有没有工具调用；如果有，就路由到 `ToolNode` 执行；执行完把结果作为消息补回状态，再回到 Agent。

### 流式输出怎么一路传到前端

模型流式输出先通过 LangGraph 事件流暴露出来，`chat_service.py` 把底层事件转成统一格式，再由 FastAPI 用 `StreamingResponse` 以 NDJSON 连续推给前端。前端一边读流，一边把 `chunk` 追加到消息，把 `tool_start` 和 `tool_end` 展示到调试面板。

### 为什么状态只存 `messages`

优点是简单、接入快、和 LangGraph 默认消息模型契合；缺点是中间业务状态不结构化，流程一复杂就会变得难维护，也不方便做精细恢复、分析和校验。

### `InMemorySaver` 的局限是什么

- 只在当前进程内有效
- 服务重启后丢失
- 不适合多实例部署
- 不方便追踪和审计

如果上生产，我会换成 Redis 或数据库做持久化 checkpointer。

## 5. 主动讲缺点和改进点

面试里建议主动承认这些点，这会显得你不是只会“跑通 demo”。

### 缺点 1：会话记忆只用 `InMemorySaver`

改进答法：

如果上生产，我会把 LangGraph 的 checkpointer 接到 Redis 或 Postgres，保证跨进程共享和重启恢复。

### 缺点 2：工具输出和异常不统一

改进答法：

我会为所有工具统一定义 schema，比如成功字段、错误字段、来源字段和可追踪 ID，让 Agent 更容易稳定消费工具结果。

### 缺点 3：景点抓取依赖 Selenium 和网页结构

改进答法：

这部分适合替换成更稳定的数据源，或者至少加缓存、超时和降级策略，避免页面结构变化导致主链路失效。

### 缺点 4：流程约束过多放在 prompt

改进答法：

我会把强约束下沉到代码，比如目的地校验、工具调用次数限制、结构化状态校验，而不是完全依赖模型遵守长 prompt。

### 缺点 5：缺少测试和更强校验

改进答法：

我会补三层测试：工具层 mock 测试、图流程集成测试、接口层流式测试，同时补更明确的参数校验和日志链路。

### 缺点 6：串行工具链时延较高

改进答法：

如果后续要优化，我会分析哪些查询可以并发，比如多个景点坐标查询，或对热点信息做缓存，降低整体响应时间。

## 6. 如果面试官质疑“这是不是拼装项目”

建议答法：

我会承认这个项目确实大量依赖现成框架和第三方服务，但工程价值不在“从零造轮子”，而在于把模型、图编排、工具调用、流式接口和前端消费整合成一个完整闭环。这里真正有价值的是系统设计能力，比如怎么拆层、怎么定义 Agent 和工具边界、怎么把事件流暴露给前端、怎么处理外部依赖的不稳定性、以及如果上生产应该怎么重构。

## 7. 你最后要记住的 3 个亮点

- 它不是简单聊天机器人，而是一个多工具、多步骤的 Agent 工作流。
- 它同时有 Gradio 演示入口和 FastAPI 流式接口，展示了从原型到服务化的过渡。
- 它的短板也很真实，正好可以拿来讲工程化思考和重构方案。
