# 旅游规划机器人高频追问题库

## 1. 开场类

### Q1: 你先整体介绍一下这个项目。

答：

这是一个基于 LangGraph 的旅游规划机器人。它的核心不是让模型直接回答旅游问题，而是让模型根据当前对话决定是否调用外部工具，比如网页搜索、高德地图和景点抓取，然后把这些结果整合成更完整的旅游方案。整体链路是前端或 Gradio 接收消息，交给 `chat_service.py`，进入 LangGraph 图，再由 Agent 和 ToolNode 循环执行，最后通过流式接口把结果返回前端。

### Q2: 你在这个项目里最想体现什么能力？

答：

我最想体现的是 AI 应用的系统化落地能力，不只是调一个模型接口，而是把模型决策、工具调用、状态管理、流式返回和前端展示组合成一个完整闭环。

## 2. 架构类

### Q3: 为什么要用 LangGraph？

答：

因为旅游规划是多步任务。模型可能先要明确目的地，再获取景点，再查坐标和交通，最后再生成行程。这不是一次函数调用能稳定完成的，更适合放到一个有状态、有循环的图里执行。

### Q4: LangChain 和 LangGraph 各自负责什么？

答：

LangChain 主要负责模型封装、工具绑定、消息抽象这些组件能力；LangGraph 负责把这些组件组织成状态流转和节点执行逻辑。简单说，LangChain 更像零件库，LangGraph 更像工作流引擎。

### Q5: 这个图为什么只有两个核心节点？

答：

当前实现偏 demo 化，所以把决策都集中在 Agent，把外部调用都集中在 ToolNode，结构足够简单，便于快速跑通。代价是业务语义不够清晰，如果上生产，我会拆成更明确的规划、校验、总结等节点。

## 3. Agent 和工具类

### Q6: 这个项目里 Agent 的“决策”具体体现在哪里？

答：

Agent 的核心决策是：当前要不要调用工具、调哪个工具、带什么参数、拿到工具结果之后是继续查还是直接回答。这个决策是由模型在绑定工具后，根据 prompt 和当前消息上下文生成 tool calls 来完成的。

### Q7: 为什么要绑定这么多工具？

答：

因为旅游规划涉及的信息种类很多，单靠模型内部知识不够。比如坐标和路线是地图问题，景点详情偏实时网页信息，POI 则是周边资源问题。工具的作用是给模型补事实。

### Q8: 工具调用失败会发生什么？

答：

当前项目不同工具的处理方式不完全一致。有些会返回带 `error` 字段的结果，有些会直接抛异常。异常最终会在事件流里转成错误事件返回前端。这也正是一个改进点，我会统一工具输出和错误模型。

### Q9: `save_info_and_clear_history` 真正清历史了吗？

答：

从当前代码看，它更多是返回一个 `content_and_artifact` 形式的工具结果，并没有真正更新图状态。注释里也写了，LangGraph 工具本身不直接改状态，真正的状态处理还得在主逻辑里接。

## 4. 状态和记忆类

### Q10: 为什么状态只保存 `messages`？

答：

这是一个最简设计。好处是实现快、和 LangGraph 的消息机制天然兼容；缺点是所有中间信息都混在消息里，不够结构化。业务再复杂一点，就会出现状态难追踪、难校验的问题。

### Q11: `thread_id` 的作用是什么？

答：

`thread_id` 是会话隔离键，LangGraph 的 checkpointer 会用它区分不同会话的状态。同一个 `thread_id` 的后续请求会复用同一条对话上下文。

### Q12: `InMemorySaver` 为什么不适合生产？

答：

因为它只保存在进程内存里，服务重启就没了，也不支持多实例共享。如果线上有多台服务，同一个用户请求落到不同实例上，会话上下文就断掉了。

## 5. 流式输出类

### Q13: 这个项目的流式输出链路怎么工作的？

答：

LangGraph 在执行时会产生事件流，`chat_service.py` 监听这些事件，把模型 token 流、工具开始和工具结束都标准化。FastAPI 通过 `StreamingResponse` 持续返回 NDJSON，前端一边读取一边更新消息和调试面板。

### Q14: 为什么不用 WebSocket？

答：

当前场景只需要单向流式下发，HTTP streaming 成本更低，实现也更直接。WebSocket 更适合双向实时互动更强的场景，但对这个 demo 来说不是必须。

## 6. 工程化和稳定性类

### Q15: 这个项目最大的稳定性风险是什么？

答：

我会说有三类。第一类是第三方 API，比如 DashScope 和高德；第二类是 Selenium 和网页 DOM 变化；第三类是 prompt 驱动的长链路执行，模型不一定每次都稳定按预期走。

### Q16: 如果要上生产，你会优先改什么？

答：

我会优先做四件事：记忆持久化、统一工具 schema、抓取链路降级、补日志和 tracing。因为这四项最直接决定可用性和排障效率。

### Q17: 这个项目有什么性能问题？

答：

主要是工具链偏串行，而且有网页抓取和外部 API 调用，整体时延会比较高。优化方向包括缓存、可并发查询的并发化，以及减少不必要工具调用。

### Q18: 编码乱码问题你怎么看？

答：

从仓库里能看到部分旧文档和模板存在编码历史痕迹，这说明文本文件编码管理不统一。短期会影响可读性，长期会影响前端展示和协作，我会统一到 UTF-8 并在编辑器和仓库层面固定编码规范。

## 7. 深挖与反质疑类

### Q19: 如果面试官说“这不就是调包吗？”

答：

我会说，AI 应用工程本来就不是从零造模型，而是把模型能力产品化。这个项目的价值在于工作流编排、工具边界设计、流式服务化、异常处理和可扩展性思考。真正难的部分是把一个不稳定的模型系统组织成可演示、可迭代的应用。

### Q20: 你觉得这个项目哪里最不像生产代码？

答：

我会点三个地方：记忆是内存级、工具输出不统一、复杂流程主要靠 prompt 控制。这三个点都说明它更像一个能工作的 demo，而不是完全工程化的服务。

### Q21: 如果让你重构，你会怎么拆？

答：

我会把现在的“单 Agent + 单 ToolNode”升级成更显式的流程，比如目的地澄清、景点采集、交通规划、住宿餐饮推荐、最终汇总几个阶段；同时把关键中间状态结构化存储，而不是全塞在消息里。

## 8. 你可以反问面试官的问题

- 如果团队现在也在做 Agent 应用，大家更关注效果稳定性还是交付速度？
- 线上 AI 应用的观测体系通常做到什么粒度，比如是否会记录 tool trace 和 prompt version？
- 团队在多工具编排时，更偏 LangGraph 这类框架，还是更偏自研 orchestration？

## 9. 临场回答技巧

- 先讲“职责”，再讲“为什么这样设计”，最后讲“局限和改进”。
- 不要把所有功劳都归给模型，要多强调系统编排和工程约束。
- 不要回避缺点，但每个缺点都给一个落地改法。
- 如果被追到很细，就顺着真实代码讲，不要发散到理想化方案。
