## 当前行为说明

### 1. 本地开发环境

默认 `APP_ENV=development`。

特点：

- 不强制启动时必须有真实 API key；
- 默认允许本地前端和本地 API 来源；
- 工具或模型真正需要密钥时，仍会返回清晰的缺失错误；
- 适合本地测试和导入模块。

### 2. 测试环境

测试中通过 `tests/conftest.py` 自动清理 settings 缓存。

特点：

- 每个测试可以独立设置环境变量；
- 不会因为前一个测试缓存了 settings 而污染后续测试；
- 不依赖真实 DashScope 或高德密钥。

### 3. 生产环境

当 `APP_ENV=production` 时：

- 默认 `REQUIRE_API_KEYS=true`；
- 缺少 `DASHSCOPE_API_KEY` 会启动失败；
- 缺少 `AMAP_API_KEY` 会启动失败；
- `CORS_ORIGINS=*` 会启动失败；
- 必须显式配置可信前端来源。

## 遗留事项

1. `CACHE_ENABLED` 只是配置预留。

   后续第六阶段需要真正接入坐标、景点、POI、路线和搜索结果的 TTL 缓存。

2. `tools/static_map.py` 仍是旧工具形态。

   本阶段只完成密钥来源统一，没有重构文件输出路径、错误处理和返回协议。后续可在工具清理阶段继续处理。

3. `settings.py` 当前使用标准库 dataclass 实现。

   这避免新增依赖。如果后续配置项继续增多，可以考虑迁移到 `pydantic-settings`，但需要同步更新依赖和测试。

4. CORS 当前仍允许任意方法和任意请求头。

   本阶段重点先收紧来源。生产化时可以进一步细化 `allow_methods` 和 `allow_headers`。

5. 运行时修改环境变量不会自动热更新已导入模块常量。

   当前配置适合进程启动时读取。如果后续需要动态刷新配置，应增加显式 reload 机制。

## 后续建议

下一阶段建议进入“缓存与会话持久化”，重点处理：

- 为地点坐标、景点信息、周边 POI、交通路线和搜索结果增加 TTL 缓存；
- 按查询参数生成稳定 cache key；
- 将 `InMemorySaver` 替换为 SQLite、Postgres 或 Redis checkpointer；
- 让服务重启后仍能恢复会话状态；
- 结合第五阶段的 `CACHE_ENABLED` 配置控制缓存开关。
