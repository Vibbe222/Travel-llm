# 第七阶段补充优化方案：前置计划摘要与降级提示

## 1. 补充优化原因

第七阶段已经加入了 `progress` 事件、停止生成、新建会话、工具调用面板、错误分层展示和降级提示框。但在本地验收时发现两个体验问题：

### 1.1 用户输入后仍可能长时间看不到正文

当前 advanced 结构化流程为了避免泄漏内部信息，只放行 `final_responder` 节点的模型流：

```python
if node_name and node_name != STREAMING_RESPONSE_NODE:
    return None
```

这能避免把早期阶段的内部 JSON、Prompt、调试信息、模型中间输出直接暴露给用户。

这个过滤逻辑是必要的。因为 advanced 流程和原 main 分支最大的差异是：advanced 已经不再是“模型边想边答”的单段聊天流，而是一个多节点、结构化、带工具调用和状态写入的工作流。

在这个工作流中，早期节点承担的是内部决策职责，而不是直接面向用户输出最终内容。例如：

- `intent_router` 负责识别用户意图、目的地、天数、偏好等结构化字段；
- `attraction_collector` 负责调用景点工具，并把景点列表、开放时间、建议停留时长等写入状态；
- `itinerary_planner` 负责生成结构化日程；
- `transport_validator` 负责检查景点之间的交通可行性；
- `poi_enricher` 负责补充餐饮、住宿等周边信息。

这些节点执行过程中产生的内容往往不是稳定的用户文案，而可能是：

- 模型返回的 JSON；
- 工具入参和工具原始返回；
- 节点间传递的中间状态；
- fallback 原因；
- 校验问题；
- 调试字段；
- 不完整的草稿。

如果把这些内容像 main 分支一样直接流给用户，会产生几个问题：

1. 用户可能看到 JSON、字段名、工具名等内部实现细节；
2. 用户可能看到尚未校验的中间草稿，误以为这是最终结果；
3. 模型输出如果格式错误，会把错误格式直接暴露在聊天正文里；
4. 工具返回里可能包含过长、过乱或偏技术化的信息；
5. 一旦未来工具或 Prompt 中出现敏感字段，直出会增加泄漏风险；
6. 聊天正文会混入“系统执行过程”和“最终旅行建议”，降低可读性。

因此，不能简单取消这段过滤逻辑，也不建议恢复原 main 分支“早期模型流直接吐给用户”的方式。

但这个安全设计也带来了明显副作用：

- `intent_router`
- `attraction_collector`
- `itinerary_planner`
- `transport_validator`
- `poi_enricher`

这些节点执行期间，用户在聊天正文里可能看不到任何内容。即使右侧调试面板在更新，普通用户仍会感觉“系统卡住了”。

这个问题在旅游规划场景里尤其明显。因为一次完整规划通常要经历：

```text
识别目的地
  -> 获取景点
  -> 补全坐标
  -> 生成行程
  -> 校验交通
  -> 补充餐饮住宿
  -> 组织最终回复
```

其中景点抓取、地图接口、交通接口、网页搜索都可能耗时。用户点击“发送”后，如果聊天正文长时间没有变化，即使系统实际正在工作，用户也很难判断：

- 请求是否已经发出；
- 后端是否收到；
- 模型是否卡住；
- 工具是否失败；
- 页面是否无响应；
- 是否需要重复点击发送。

这会直接影响验收体验。对于一个面向用户的旅行规划助手来说，“系统是否正在理解并处理我的需求”本身就是关键反馈。

原 main 分支的体验更快，是因为早期模型输出会直接流给用户，用户很快能看到类似“我将先查询景点信息”的文字。这个体验优点需要保留，但实现方式要改变：

- 不能直接恢复早期模型流；
- 不能把内部节点输出原样给用户；
- 应该由后端在关键节点完成后，手动构造一段安全、稳定、用户可理解的前置说明。

因此，本次补充优化的目标是：

> 保留 advanced 的安全过滤机制，同时显式构造一段用户可见的“前置计划摘要”，让用户尽早看到系统已经理解任务并开始执行。

这段“前置计划摘要”的定位不是模型思考，也不是内部推理，而是系统对用户需求的可见确认和执行说明。

它要回答用户最关心的四个问题：

| 用户关心的问题 | 前置摘要中的对应内容 |
|---|---|
| 系统理解我要做什么了吗 | `任务` |
| 系统是否识别出了目的地和上下文 | `回顾` |
| 系统接下来为什么要查这些信息 | `分析` |
| 系统下一步会调用什么能力 | `计划` |

推荐格式：

```text
任务：用户明确想去福州游玩两天，需要获取福州的景点信息。
回顾：用户描述了本次旅行需求，目的地已明确为“福州”。
分析：需要先获取福州的景点信息，包括景点简介、开放时间和预计游玩时间等。
计划：调用“景点搜索工具”获取福州的景点列表。

```

这里使用“分析”，不用“思考”，原因是：

- “思考”容易让用户误以为系统在展示模型内部推理；
- “分析”更像产品化的执行说明；
- 这段内容由后端模板构造，不是模型链路的隐藏推理。

前置摘要的生成时机也需要明确：

```text
用户发送消息
  -> 后端收到请求，先发通用 progress
  -> intent_router 真实识别完成
  -> 如果识别出目的地，立刻发送前置计划摘要
  -> 后续继续工具调用和最终行程生成
```

也就是说，它不是前端根据用户输入硬猜出来的占位文本，而是后端基于真实识别结果生成的安全摘要。这样可以避免用户输入格式不标准时，前端错误猜测目的地或天数。

同时，它仍然比等待最终行程完成更快，因为它只需要等 `intent_router` 完成，不需要等景点抓取、交通校验和最终回复全部结束。

这次优化的边界是：

- 前置摘要只展示用户可理解的任务、回顾、分析和计划；
- 不展示 Prompt；
- 不展示 JSON；
- 不展示模型内部推理；
- 不展示工具原始返回；
- 不展示 API key、token 等敏感信息；
- 不替代最终行程，只作为最终行程前的开头说明；
- 如果没有识别出明确目的地，不生成前置计划摘要，而是立即反问用户补充目的地。

### 1.2 fallback 降级提示没有足够明显或足够具体

验收截图中可以看到，工具调试面板里已经出现：

```json
"source": "web_search_fallback",
"fallback_used": true
```

这说明系统确实已经从主景点抓取降级到了 web search。

但用户侧没有看到足够明确的独立提示，问题包括：

- 降级信息主要藏在右侧工具 JSON 里；
- 普通用户难以理解 `web_search_fallback`；
- 没有明确说明“哪个组件出问题”；
- 没有明确说明“为什么改用网页搜索”；
- 没有明确说明“结果会受到什么影响”。

因此，本次补充优化还需要增强降级提示，让它成为用户可见信息，而不是只作为调试日志存在。

## 2. 本次补充优化目标

本次补充优化要实现以下目标：

1. 用户输入后，后端完成真实意图识别后，尽快在助手消息正文中输出一段安全的前置计划摘要；
2. 前置计划摘要模拟原 main 分支“快速初步回应”的体验；
3. 前置计划摘要不暴露内部 Prompt、JSON、模型中间推理或 API 密钥；
4. 后续最终行程继续追加到同一个助手消息中；
5. 如果未识别出明确目的地，立即中止本轮规划并反问用户，不继续调用景点搜索等重工具；
6. 当景点抓取降级为 web search 时，前端必须展示独立降级提示；
7. 降级提示要明确指出出问题的组件、原因、影响和可信度。

## 3. 不做事项

本次补充优化不做以下事项：

- 不取消早期模型流过滤；
- 不恢复 main 分支“所有早期模型输出直接吐给用户”的行为；
- 不暴露 `intent_router` 的原始 JSON；
- 不暴露 Prompt；
- 不展示模型中间推理；
- 不新增前端框架；
- 不重构整套 LangGraph 节点；
- 不实现服务端历史会话存储；
- 不要求工具调试面板默认折叠。

## 4. 核心设计

### 4.1 保留安全过滤逻辑

继续保留：

```python
if node_name and node_name != STREAMING_RESPONSE_NODE:
    return None
```

原因：

- `intent_router` 等早期节点可能输出结构化 JSON；
- 这些内容面向系统，不面向用户；
- 直接放行会降低产品可信度，并可能暴露内部实现。

### 4.2 显式构造用户可见前置计划摘要

在 `intent_router` 真实识别完成后，由后端根据结构化结果手动构造一段安全文本。

示例：

```text
任务：用户明确想去福州游玩两天，需要获取福州的景点信息。
回顾：用户描述了本次旅行需求，目的地已明确为“福州”。
分析：需要先获取福州的景点信息，包括景点简介、开放时间和预计游玩时间等。
计划：调用“景点搜索工具”获取福州的景点列表。

```

说明：

- “思考”统一改成“分析”；
- 不使用模型内部思考；
- 不展示 JSON；
- 不展示 Prompt；
- 文案由后端安全模板生成；
- 通过 `chunk` 事件发送给前端；
- 前端无需新增特殊处理，直接追加到助手消息开头。

### 4.3 最终行程继续追加到同一助手消息

流式顺序应为：

```text
用户发送需求
  -> progress: 已收到请求，正在识别目的地
  -> intent_router 完成
  -> chunk: 前置计划摘要
  -> 继续调用景点、交通、周边等工具
  -> final_responder chunk: 最终行程正文
  -> done
```

最终用户看到的是同一条助手消息：

```text
任务：...
回顾：...
分析：...
计划：...

# 福州两日游行程
...
```

## 5. 未识别目的地时的行为

用户已经明确要求：

> 未识别出目的地就立刻中止并反问用户。

因此本次补充优化中，未识别目的地时不再继续调用：

- 目的地候选搜索；
- 景点搜索；
- 坐标补全；
- 交通校验；
- 周边 POI；
- 最终完整行程生成。

推荐行为：

```text
我还没有识别出明确目的地。请补充你想去的城市或地区，例如“福州两天”“杭州周末游”。
```

推荐图路由：

```text
intent_router
  -> selected_destination 存在：attraction_collector
  -> selected_destination 不存在：clarification_responder -> END
```

如果暂不新增节点，也可以先让 `intent_router` 写入明确澄清消息，并让路由直接结束。

但不推荐继续走现有 `destination_clarifier`，因为它可能调用 web search 搜候选目的地，这与“未识别目的地立即中止”冲突。

## 6. 推荐后端改动

### 6.1 `chat_service.py`

监听 `intent_router` 的 `on_chain_end` 事件。

从事件输出里提取：

- `selected_destination`
- `user_constraints`
- `intent_type`
- `needs_clarification`

注意：

LangGraph / LangChain 的事件输出可能有包装结构，因此实现时应兼容：

- `event["data"]["output"]`
- `event["data"]["output"]["output"]`
- 直接状态片段；
- 其他可能包装。

推荐新增函数：

```python
def _build_user_plan_preface(output: dict) -> str:
    destination = output.get("selected_destination") or ""
    constraints = output.get("user_constraints") or {}
    days = constraints.get("days")

    day_text = f"{days}天" if days else "本次"

    return (
        f"任务：用户明确想去{destination}游玩{day_text}，需要获取{destination}的景点信息。\n"
        f"回顾：用户描述了本次旅行需求，目的地已明确为“{destination}”。\n"
        f"分析：需要先获取{destination}的景点信息，包括景点简介、开放时间和预计游玩时间等。\n"
        f"计划：调用“景点搜索工具”获取{destination}的景点列表。\n\n"
    )
```

发送方式：

```json
{
  "type": "chunk",
  "content": "任务：...\n回顾：...\n分析：...\n计划：...\n\n"
}
```

为避免重复输出，需要在 `iter_chat_events` 中增加本轮布尔标记：

```python
preface_sent = False
```

同一轮只允许发送一次前置计划摘要。

### 6.2 `graph/routers.py`

调整未识别目的地时的路由。

目标：

```text
needs_clarification=True -> 澄清回复 -> END
```

不要继续进入 `destination_clarifier` 做候选搜索。

### 6.3 `graph/nodes.py`

必要时新增轻量澄清节点，例如：

```text
clarification_responder
```

职责：

- 输出澄清问题；
- 不调用外部工具；
- 不进入完整行程生成链路。

示例回复：

```text
我还没有识别出明确目的地。请补充你想去的城市或地区，例如“福州两天”“杭州周末游”。
```

## 7. 降级提示增强

### 7.1 识别条件

当工具返回：

```json
{
  "success": true,
  "data": {
    "source": "web_search_fallback",
    "fallback_used": true
  }
}
```

后端必须发出 `degradation` 事件。

### 7.2 降级提示内容

提示必须包含：

- 出问题的组件；
- 原因；
- 影响；
- 可信度；
- 调试详情。

推荐文案：

```text
降级提示
出问题的组件：景点主数据源抓取组件（get_attractions_information / Selenium）
原因：Chrome WebDriver 启动或页面抓取失败，已改用网页搜索结果。
影响：景点简介、开放时间和建议游玩时长可能不完整。
可信度：中等
```

### 7.3 组件映射

建议在 `chat_service.py` 中增加组件映射：

| 工具名 | 用户可见组件 |
|---|---|
| `get_attractions_information` | 景点主数据源抓取组件（get_attractions_information / Selenium） |
| `get_location_coordinate` | 地点坐标解析组件（get_location_coordinate / AMap） |
| `route_planning` | 交通路线规划组件（route_planning / AMap） |
| `search_nearby_poi` | 周边 POI 查询组件（search_nearby_poi / AMap） |
| `web_search` | 网页搜索组件（web_search / DuckDuckGo） |

### 7.4 原因提取

优先从工具返回的 `warnings` 中提取具体原因。

例如：

```json
"warnings": [
  "Selenium 景点抓取失败，已降级使用网页搜索。原因摘要：WebDriverException: Message: chrome failed"
]
```

可归纳为：

```text
Chrome WebDriver 启动或页面抓取失败，已改用网页搜索结果。
```

如果没有 warnings，则使用默认原因：

```text
主数据源不可用，已改用备用数据来源。
```

## 8. 用户可见行为

### 8.1 正常识别目的地

用户输入：

```text
福州两天怎么玩
```

预期行为：

```text
任务：用户明确想去福州游玩两天，需要获取福州的景点信息。
回顾：用户描述了本次旅行需求，目的地已明确为“福州”。
分析：需要先获取福州的景点信息，包括景点简介、开放时间和预计游玩时间等。
计划：调用“景点搜索工具”获取福州的景点列表。

后续继续输出完整福州两日游行程。
```

### 8.2 未识别目的地

用户输入：

```text
帮我规划两天轻松游
```

预期行为：

```text
我还没有识别出明确目的地。请补充你想去的城市或地区，例如“福州两天”“杭州周末游”。
```

系统不继续调用景点搜索、交通、周边 POI 等工具。

### 8.3 景点抓取降级

当 `get_attractions_information` 发生 `web_search_fallback`：

预期前端显示：


右侧工具调试面板仍可保留原始 JSON。

## 9. 验收标准

本次补充优化完成后，应满足：

- 用户输入明确目的地后，`intent_router` 识别完成即输出前置计划摘要；
- 前置计划摘要作为助手消息开头；
- 最终行程继续追加到同一助手消息；
- 前置摘要不暴露内部 JSON、Prompt、模型中间推理或 API 密钥；
- 未识别目的地时立即反问用户；
- 未识别目的地时不调用景点搜索工具；
- 降级到 `web_search_fallback` 时，聊天区出现独立降级提示；
- 降级提示明确说明出问题组件；
- 降级提示明确说明原因、影响和可信度；
- 右侧工具调试面板仍保留原始工具调用日志；
- 原有完整测试套件通过。

## 10. 风险与注意事项

1. `on_chain_end` 事件输出结构可能随 LangGraph / LangChain 版本变化，需要写兼容提取逻辑。
2. 如果 `intent_router` 本身很慢，前置计划摘要仍要等待它完成；在此之前可以继续显示通用 progress，例如“正在识别目的地”。
3. 前置计划摘要必须只发一次，避免图重试或事件重复导致正文重复。
4. 未识别目的地后直接结束会改变当前“候选目的地搜索”的行为，这是符合本次用户确认要求的变更。
5. 降级提示文案要足够具体，但仍需避免暴露 API key、token 等敏感信息。
