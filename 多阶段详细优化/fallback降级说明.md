# 第七阶段 fallback 降级说明

## 1. fallback 是什么

`fallback` 指“降级兜底方案”。

当主流程、主模型输出、主数据源或某个工具调用失败时，系统不直接中断，而是切换到一个更稳妥但可能不够完整的备用方案，让用户仍然可以得到一个可用结果。

简单来说：

> fallback = 出错后不中断，改用备用方案继续完成任务。

## 2. 为什么需要 fallback

旅游规划流程依赖多个不稳定因素：

- 外部网页结构可能变化；
- 地图、搜索、交通接口可能超时；
- 模型可能没有返回预期 JSON；
- 部分景点、坐标、餐饮或住宿数据可能缺失；
- 缓存里可能只有旧数据。

如果没有 fallback，任意一个环节失败都可能导致整次生成失败。

加入 fallback 后，系统可以在保证用户体验连续性的前提下，把“不完整、不确定、已降级”的部分清楚展示出来。

## 3. 当前项目中的 fallback 示例

### 3.1 景点采集 fallback

正常流程：

- 使用主数据源抓取目的地景点信息。

fallback 流程：

- 如果主数据源抓取失败，改用网页搜索结果生成候选景点。

影响：

- 景点详情、开放时间、建议停留时长可能不完整；
- 结果仍可用于生成基础行程，但可信度低于主数据源。

### 3.2 LLM JSON 解析 fallback

正常流程：

- 模型返回结构化 JSON；
- 系统解析 JSON 并写入状态。

fallback 流程：

- 如果模型返回内容不是合法 JSON，则使用规则生成基础结构。

影响：

- 行程可继续生成；
- 但路线细节、时间安排和个性化程度可能下降。

### 3.3 工具调用失败 fallback

正常流程：

- 调用地图、周边、交通等工具补充外部数据。

fallback 流程：

- 如果工具失败，则跳过失败工具或使用已有数据继续生成。

影响：

- 坐标、交通、餐饮、住宿等部分信息可能缺失；
- 最终结果需要给用户明确提示。

## 4. fallback 与错误的区别

| 类型 | 含义 | 是否继续主流程 | 前端展示方式 |
| --- | --- | --- | --- |
| 普通错误 | 某个环节失败，可能导致流程中断 | 不一定 | 错误提示 |
| 工具错误 | 外部工具调用失败 | 通常继续 | 用户可读错误 + 调试详情 |
| fallback | 主方案失败后启用备用方案 | 继续 | 降级提示框 |
| 缓存旧数据 | 实时数据不可用，使用缓存 | 继续 | 降级提示框 |
| 不完整数据 | 只拿到部分结果 | 继续 | 降级提示框 |

## 5. 第七阶段前端如何展示 fallback

第七阶段新增了“降级提示框”。

当系统发生 fallback、使用缓存旧数据、跳过失败工具、改用规则生成或采用不完整数据时，前端应单独展示：

- 降级原因；
- 影响范围；
- 当前结果可信度；
- 调试模式下的阶段、工具名、错误类型和原始错误摘要。

降级提示不打断主流程，但必须让用户明显看到。

## 6. 推荐展示文案

示例：

```text
降级提示
原因：主数据源不可用，已改用备用数据来源。
影响：景点详情、开放时间或停留时长可能不如主数据源完整。
可信度：中等
```

调试详情示例：

```json
{
  "stage": "tool",
  "tool": "get_attractions_information",
  "error_type": "fallback_used",
  "source": "web_search_fallback",
  "warnings": ["Selenium 景点抓取失败，已降级使用网页搜索。"]
}
```

## 7. 设计原则

1. 不把 fallback 伪装成正常结果。
2. 不向用户暴露内部 Prompt、模型中间推理或 API 密钥。
3. 用户看到的是原因和影响，不是底层异常堆栈。
4. 调试详情只用于开发和排查问题。
5. fallback 后的结果应标注可信度，避免用户误以为数据完全可靠。

## 8. 一句话总结

`fallback` 是系统的兜底机制：让生成流程在部分失败时继续产出可用结果，同时用降级提示明确告诉用户“哪里降级了、影响什么、可信度如何”。
