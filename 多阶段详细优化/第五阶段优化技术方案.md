# 第五阶段优化技术方案

## 背景与目标

第四阶段已经完成 Prompt 拆分和结构化 JSON fallback。当前项目的核心业务链路已经逐步稳定，但运行配置仍然分散在多个文件中：模型名、DashScope base_url、API key、请求超时、日志级别和 CORS 策略分别由不同模块自行读取或硬编码。

这种方式适合 Demo 快速运行，但不利于多环境部署：本地、测试和生产环境的配置边界不清晰，生产环境容易继续沿用开发时的宽松 CORS；新人也难以从仓库中判断 `.env` 需要配置哪些字段。

第五阶段目标是新增统一配置层，让项目适合本地、测试、生产多环境运行，并把安全相关配置集中校验。

## 配置中心设计

新增 `settings.py`，提供统一配置对象：

```python
settings = get_settings()
```

配置字段：

| 字段 | 环境变量 | 说明 |
|---|---|---|
| `app_env` | `APP_ENV` | 运行环境：development / testing / production |
| `model_name` | `MODEL_NAME` | 默认模型名 |
| `dashscope_base_url` | `DASHSCOPE_BASE_URL` | DashScope OpenAI 兼容接口地址 |
| `dashscope_api_key` | `DASHSCOPE_API_KEY` | DashScope API key |
| `amap_api_key` | `AMAP_API_KEY` | 高德 API key |
| `request_timeout_seconds` | `REQUEST_TIMEOUT_SECONDS` | 外部 HTTP 请求超时 |
| `max_retries` | `MAX_RETRIES` | 外部请求最大重试次数 |
| `cache_enabled` | `CACHE_ENABLED` | 后续缓存开关预留 |
| `log_level` | `LOG_LEVEL` | 日志级别 |
| `cors_origins` | `CORS_ORIGINS` | 允许访问 API 的前端来源 |
| `cors_allow_credentials` | `CORS_ALLOW_CREDENTIALS` | 是否允许跨域携带凭证 |
| `require_api_keys` | `REQUIRE_API_KEYS` | 是否启动时强制要求 API key |

## 默认值策略

本阶段采用“开发友好、生产严格”的默认策略：

- 默认 `APP_ENV=development`；
- 默认模型为 `deepseek-v4-flash`；
- 默认 DashScope base_url 为 `https://dashscope.aliyuncs.com/compatible-mode/v1`；
- 默认请求超时为 12 秒；
- 默认最大重试次数为 2；
- 默认日志级别为 `INFO`；
- 默认 CORS 只允许本地常见开发来源：
  - `http://localhost:3000`
  - `http://127.0.0.1:3000`
  - `http://localhost:8000`
  - `http://127.0.0.1:8000`
- `production` 环境默认要求 API key；
- `development` 和 `testing` 环境不在导入时强制要求真实 API key。

## 校验策略

`Settings.validate()` 负责集中校验：

1. `APP_ENV` 必须是 `development`、`testing` 或 `production`。
2. `MODEL_NAME` 不能为空。
3. `DASHSCOPE_BASE_URL` 不能为空。
4. `REQUEST_TIMEOUT_SECONDS` 必须大于 0。
5. `MAX_RETRIES` 必须大于等于 0。
6. `CORS_ORIGINS` 至少包含一个来源。
7. 生产环境禁止 `CORS_ORIGINS=*`。
8. 当 `REQUIRE_API_KEYS=true` 时，必须存在：
   - `DASHSCOPE_API_KEY`
   - `AMAP_API_KEY`
9. `LOG_LEVEL` 必须是 Python logging 可识别的级别。

如果配置不合法，会抛出 `SettingsError`，让启动失败尽早暴露。

## CORS 安全策略

原行为：

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

问题：

- 任意来源都可以访问 API；
- 与 `allow_credentials=True` 组合时不适合生产环境；
- 前端域名变更需要改代码。

新行为：

```python
settings = get_settings()

app.add_middleware(
    CORSMiddleware,
    allow_origins=list(settings.cors_origins),
    allow_credentials=settings.cors_allow_credentials,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

效果：

- 本地开发仍方便联调；
- 生产环境通过 `CORS_ORIGINS` 显式配置可信前端；
- 生产环境如果继续使用 `*` 会直接配置校验失败；
- CORS 策略不再硬编码在 `api/main.py` 中。

## 模型配置接入

### `chat_service.py`

原先硬编码：

```python
DEFAULT_MODEL_NAME = "deepseek-v4-flash"
```

改为：

```python
DEFAULT_MODEL_NAME = get_settings().model_name
```

### `models/qwen_factory.py`

原先硬编码：

- `BASE_URL`
- `DEFAULT_MODEL`
- `os.getenv("DASHSCOPE_API_KEY")`

改为统一读取：

- `settings.model_name`
- `settings.dashscope_base_url`
- `settings.dashscope_api_key`

模型真正初始化时仍会检查 `DASHSCOPE_API_KEY`，缺失时给出清晰错误。

## `.env.example` 设计

新增 `.env.example`，明确项目需要的环境变量：

```env
APP_ENV=development
MODEL_NAME=deepseek-v4-flash
DASHSCOPE_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
DASHSCOPE_API_KEY=your_dashscope_api_key
AMAP_API_KEY=your_amap_api_key
REQUEST_TIMEOUT_SECONDS=12
MAX_RETRIES=2
CACHE_ENABLED=false
LOG_LEVEL=INFO
CORS_ORIGINS=http://localhost:3000,http://127.0.0.1:3000,http://localhost:8000,http://127.0.0.1:8000
CORS_ALLOW_CREDENTIALS=true
REQUIRE_API_KEYS=false
```

`.gitignore` 已保留：

```text
.env
.env.*
!.env.example
```

因此真实密钥不会提交，示例文件会被纳入仓库。

## 风险与注意事项

1. `settings.py` 使用 `lru_cache` 缓存配置，测试中修改环境变量后需要清理缓存。当前通过 `tests/conftest.py` 自动处理。
2. `tools/base.py` 的 `DEFAULT_TIMEOUT_SECONDS` 和 `DEFAULT_MAX_RETRIES` 在导入时读取配置。运行中动态修改环境变量不会自动改变已导入常量，后续如果需要运行时热更新，应改为每次请求时读取 settings。
3. 生产环境是否要求 API key 由 `REQUIRE_API_KEYS` 控制，默认在 `APP_ENV=production` 时为 true。开发环境仍允许缺失密钥，以便测试和导入不被真实凭证阻塞。
4. `CACHE_ENABLED` 目前只是配置预留，第六阶段才会真正接入缓存逻辑。
5. `tools/static_map.py` 仍是旧工具形态，当前只完成密钥读取接入，没有重构其输出路径和错误处理；该问题可放到后续文件职责优化或工具层补强中处理。
