# 第四阶段优化技术方案

## 背景与目标

第三阶段已经将正式入口从单 Agent + ToolNode 循环升级为结构化状态 + 多节点 LangGraph 流程，并新增了意图识别、目的地澄清、景点采集、行程规划、交通校验、餐住推荐和最终回复等节点。

在第三阶段中，阶段 Prompt 已经初步拆到 `prompts/intent.py`、`prompts/clarify.py`、`prompts/planner.py`、`prompts/validation.py` 和 `prompts/finalize.py`，但仍存在两个维护问题：

- `prompts/main.py` 仍保留旧的大段全流程 Prompt，容易让后续维护者误以为正式入口仍依赖单一大 Prompt；
- `StageExecutor` 虽然支持 `expects_json=True`，但当模型返回内容不是合法 JSON 时，没有立即进入 fallback，而是把原始文本作为普通 `content` 返回，导致结构化节点需要在外层再兜底，错误定位不够直接。

第四阶段目标是正式完成 Prompt 拆分收口：让每个 Prompt 只服务一个阶段，让结构化输出节点的 JSON 失败有统一 fallback，并通过测试锁定这些行为。

## 本阶段范围

本阶段优化对象：

- `prompts/main.py`
- `prompts/__init__.py`
- `agents/stage_executor.py`
- `tests/test_streaming_and_prompts.py`

本阶段延续已有阶段 Prompt 文件：

- `prompts/intent.py`
- `prompts/clarify.py`
- `prompts/planner.py`
- `prompts/validation.py`
- `prompts/finalize.py`

## 不做事项

本阶段不做以下事项：

- 不重新设计 LangGraph 节点拓扑；
- 不调整工具层统一返回协议；
- 不改变 `/chat/stream` 请求和响应结构；
- 不新增真实外部 API 联调；
- 不引入新的 Prompt 管理框架；
- 不引入 Pydantic schema 或 LangChain structured output 绑定；
- 不改变当前模型供应商和模型工厂；
- 不改造前端 UI；
- 不修改餐饮住宿、交通和景点采集业务逻辑。

## Prompt 拆分设计

第四阶段要求 `prompts/main.py` 不再作为大 Prompt 的承载文件，而是作为轻量聚合入口。

拆分后的职责如下：

| 文件 | 阶段 | 职责 |
|---|---|---|
| `prompts/intent.py` | 意图识别 | 识别用户意图、目的地和约束 |
| `prompts/clarify.py` | 目的地澄清 | 生成简短澄清说明或候选解释 |
| `prompts/planner.py` | 行程规划 | 基于景点和约束生成结构化 `daily_plan` |
| `prompts/validation.py` | 交通校验 | 基于交通摘要做补充性判断 |
| `prompts/finalize.py` | 最终回复 | 基于结构化状态生成用户可读 Markdown |
| `prompts/main.py` | 聚合导出 | 提供 `PROMPT_REGISTRY`，不再保存旧大 Prompt |

`PROMPT_REGISTRY` 用于集中查看当前正式阶段 Prompt：

```python
PROMPT_REGISTRY = {
    "intent": INTENT_PROMPT,
    "clarify": CLARIFY_PROMPT,
    "planner": PLANNER_PROMPT,
    "validation": VALIDATION_PROMPT,
    "finalize": FINALIZE_PROMPT,
}
```

这种设计保留了一个统一入口，方便测试、文档和未来调试工具读取 Prompt，同时避免旧 `agent_prompt_template` 继续存在造成误导。

## 各阶段 Prompt 职责

### 1. 意图识别 Prompt

文件：`prompts/intent.py`

职责：

- 读取当前状态摘要；
- 读取用户最新消息；
- 输出 `intent_type`；
- 提取 `selected_destination`；
- 提取 `user_constraints`。

输出要求：

- 必须只输出 JSON 对象；
- 不输出解释性文字；
- 外层节点通过 `StageExecutor(expects_json=True)` 解析。

### 2. 目的地澄清 Prompt

文件：`prompts/clarify.py`

职责：

- 基于当前状态和候选目的地；
- 生成一句简短说明；
- 帮助用户理解为什么需要先确认目的地。

输出要求：

- 当前不强制 JSON；
- 结果作为 `content` 使用；
- 工具搜索失败或 LLM 失败时可返回空内容，由节点生成默认澄清消息。

### 3. 行程规划 Prompt

文件：`prompts/planner.py`

职责：

- 基于已确认目的地、用户约束和景点信息；
- 生成按天组织的行程草案；
- 输出 `daily_plan`。

输出要求：

- 必须只输出 JSON 对象；
- JSON 示例中的大括号需要转义，确保 `str.format(...)` 可正常渲染；
- 外层节点解析失败时使用规则 fallback 生成基础行程骨架。

### 4. 交通校验 Prompt

文件：`prompts/validation.py`

职责：

- 接收当前状态摘要；
- 接收交通查询摘要；
- 做补充性合理性判断。

输出要求：

- 当前不强制 JSON；
- 核心交通判断仍由节点内规则完成；
- LLM 内容只作为辅助，不影响基础规则校验结果。

### 5. 最终回复 Prompt

文件：`prompts/finalize.py`

职责：

- 基于结构化状态生成中文 Markdown；
- 汇总目的地、每日行程、交通、餐饮住宿和风险提示；
- 避免暴露内部错误、API key 和完整第三方请求 URL。

输出要求：

- 当前不强制 JSON；
- LLM 不可用时使用 `_render_final_markdown(...)` 规则渲染 fallback。

## JSON 输出节点

本阶段明确需要结构化输出的节点：

- `intent_router`
- `itinerary_planner`

对应配置：

```python
StageExecutor(
    model_name=model_name,
    prompt_template=INTENT_PROMPT,
    expects_json=True,
    fallback=_fallback_intent_result,
)
```

```python
StageExecutor(
    model_name=model_name,
    prompt_template=PLANNER_PROMPT,
    expects_json=True,
    fallback=_fallback_plan_result,
)
```

设计原则：

- 能由规则稳定完成的兜底逻辑保留在节点侧；
- Prompt 只负责引导模型产出期望结构；
- JSON 解析失败统一由 `StageExecutor` 捕获并进入 fallback；
- 节点收到的结果始终优先按结构化字典处理。

## JSON 解析失败 fallback 设计

原行为：

```python
if self.expects_json:
    parsed = safe_json_loads(content)
    if parsed is not None:
        return parsed

return {"content": content}
```

问题：

- 模型返回非 JSON 时，结构化节点会收到 `{"content": "..."}`；
- `intent_router` 和 `itinerary_planner` 仍需要依靠节点外层逻辑继续兜底；
- 无法区分“普通文本输出”和“结构化输出解析失败”；
- 出错阶段定位不够清晰。

新行为：

```python
if self.expects_json:
    parsed = safe_json_loads(content)
    if parsed is not None:
        return parsed
    if self.fallback is not None:
        fallback_data = self.fallback(state)
        fallback_data.setdefault("fallback_reason", "json_parse_failed")
        return fallback_data

return {"content": content}
```

效果：

- JSON 解析失败立即进入阶段 fallback；
- fallback 结果带有 `fallback_reason="json_parse_failed"`；
- 结构化节点收到的仍是符合预期的字段；
- 单个阶段出错时更容易定位。

## `safe_json_loads` 当前能力

`safe_json_loads(text)` 当前支持：

- 直接解析 JSON 对象字符串；
- 兼容简单 Markdown fenced code block；
- 只接受 dict 类型；
- 解析失败返回 `None`。

当前暂不扩展为复杂 JSON 修复器，原因是：

- 本阶段目标是稳定失败路径，而不是尽可能猜测模型输出；
- 过度修复可能掩盖 Prompt 或模型输出问题；
- fallback 更符合当前项目“可恢复、可解释”的工程策略。

## 测试方案

本阶段新增或强化以下测试：

### 1. Prompt JSON 示例渲染测试

测试目标：

- `PLANNER_PROMPT` 中 JSON 示例的大括号已正确转义；
- `str.format(...)` 不会因为示例 JSON 抛异常；
- 渲染后仍包含 `daily_plan` 和目的地信息。

### 2. Prompt 格式化异常 fallback 测试

测试目标：

- 当 Prompt 模板缺少上下文字段时；
- `StageExecutor` 不直接抛出异常；
- 能调用 fallback 并写入 `fallback_reason`。

### 3. JSON 解析失败 fallback 测试

测试目标：

- 当 `expects_json=True` 且模型返回非 JSON；
- `StageExecutor` 立即调用 fallback；
- 返回结果包含 `fallback_reason="json_parse_failed"`。

### 4. Prompt registry 测试

测试目标：

- `PROMPT_REGISTRY` 包含五个阶段；
- `prompts/main.py` 不再保留旧大 Prompt 的“工作流程”内容；
- 后续不会误把旧 `agent_prompt_template` 当正式入口。

## 实施顺序

1. 检查现有 prompt 文件和 `graph/nodes.py` 引用关系。
2. 确认 `intent_router` 和 `itinerary_planner` 是结构化 JSON 输出节点。
3. 将 `prompts/main.py` 从旧大 Prompt 改为 `PROMPT_REGISTRY`。
4. 在 `prompts/__init__.py` 中统一导出阶段 Prompt。
5. 修改 `StageExecutor`，让 JSON 解析失败进入 fallback。
6. 补充 prompt 和 JSON fallback 回归测试。
7. 执行相关测试。
8. 执行完整测试套件。
9. 编写第四阶段技术方案和验收文档。

## 验收标准

第四阶段完成后，应满足以下标准：

- `prompts/main.py` 不再保存旧大 Prompt；
- `prompts/main.py` 提供五阶段 `PROMPT_REGISTRY`；
- 五个阶段 Prompt 文件继续独立维护；
- `prompts/__init__.py` 能统一导出阶段 Prompt；
- `intent_router` 和 `itinerary_planner` 继续要求 JSON 输出；
- JSON 解析失败时，`StageExecutor` 能调用 fallback；
- JSON 解析失败 fallback 带有可识别原因；
- Prompt 格式化异常仍能 fallback；
- 相关测试通过；
- 完整测试套件通过。

## 风险与注意事项

1. 目前 JSON schema 仍由 Prompt 文本约束，没有使用强类型 schema 校验。后续如果结构更复杂，可以引入 Pydantic 模型做二次校验。
2. `safe_json_loads` 只做轻量解析，不负责复杂修复。如果模型经常输出半结构化文本，应优先调整 Prompt 或模型调用方式。
3. `validation.py` 当前没有强制 JSON，因为交通校验的核心判断由规则完成。后续如果要让模型输出补充校验项，可以单独设计 `validation_issues` 的 JSON schema。
4. `finalize.py` 当前输出 Markdown，不要求 JSON。若后续前端需要结构化展示最终结果，可以新增“最终展示结构”而不是直接改 Markdown 输出。
5. `prompts/main.py` 删除旧大 Prompt 后，历史 `Agent` 类如果仍尝试导入 `agent_prompt_template` 会失败。当前正式入口不再依赖它；如需保留旧 Agent 演示入口，应单独创建 legacy prompt 文件，避免污染正式 Prompt 结构。
