# 第三阶段优化技术方案

## 背景与目标

第一阶段已经稳定工具层，第二阶段补齐基础测试。当前正式入口仍然是单一 Agent 通过一个大 Prompt 控制完整旅游规划流程，再通过 ToolNode 循环调用工具。

这种方式的问题是：流程控制、信息抽取、工具调用、行程规划、交通校验、餐住推荐和最终回复都压在同一个 Prompt 中，复杂度高，状态难沉淀，后续扩展新能力时容易出现不可控回归。

第三阶段目标是将正式 LangGraph 入口升级为结构化状态和多节点流程，让每个节点负责一个明确阶段，工具结果沉淀到状态字段中，降低大 Prompt 控制复杂流程的不确定性。

## 结构化状态设计

正式状态升级为 `TravelPlannerState`，并保留 `PublicState` 兼容旧导入。

核心字段：

- `messages`：对话消息，继续使用 `add_messages` 累积；
- `intent_type`：用户意图类型，例如 `new_plan`、`modify`、`confirm`；
- `selected_destination`：已确认或默认选择的目的地；
- `user_constraints`：天数、预算、风格、餐住偏好等约束；
- `candidate_destinations`：目的地不明确时的候选列表；
- `attractions`：景点采集和坐标补全后的结构化结果；
- `daily_plan`：按天组织的行程草案；
- `transport_segments`：景点间交通查询结果；
- `meal_options`：餐饮候选；
- `hotel_options`：住宿候选；
- `validation_issues`：流程中发现的问题和降级提示；
- `needs_clarification`：是否需要目的地澄清；
- `needs_replan`：是否需要重排行程；
- `replan_attempts`：重排次数；
- `final_status`：当前阶段状态标记。

## 图结构设计

正式图从单 Agent 循环升级为以下节点：

```text
START
  -> intent_router
  -> destination_clarifier 或 attraction_collector 或 itinerary_planner 或 final_responder
  -> attraction_collector
  -> itinerary_planner
  -> transport_validator
  -> itinerary_planner 或 poi_enricher
  -> final_responder
  -> END
```

节点职责：

### 1. 意图识别节点 `intent_router`

职责：

- 读取最新用户消息；
- 识别 `intent_type`；
- 抽取目的地；
- 抽取用户约束；
- 判断是否需要目的地澄清。

输出字段：

- `intent_type`
- `selected_destination`
- `user_constraints`
- `needs_clarification`
- `validation_issues`

### 2. 目的地澄清节点 `destination_clarifier`

职责：

- 当用户没有给出明确目的地时，通过 `web_search` 获取候选目的地；
- 将候选结果写入 `candidate_destinations`；
- 在参考版中默认选择一个候选继续流程；
- 必要时向 `messages` 写入澄清说明。

输出字段：

- `candidate_destinations`
- `selected_destination`
- `needs_clarification`
- `messages`

### 3. 景点采集节点 `attraction_collector`

职责：

- 调用 `get_attractions_information` 获取目的地景点；
- 调用 `get_location_coordinate` 补全每个景点坐标；
- 将景点、开放时间、游玩时长、坐标和城市编码沉淀到 `attractions`；
- 采集失败或坐标失败时写入 `validation_issues`。

输出字段：

- `attractions`
- `validation_issues`

### 4. 行程规划节点 `itinerary_planner`

职责：

- 基于 `attractions` 和 `user_constraints` 生成 `daily_plan`；
- 优先使用阶段 Prompt 输出结构化 JSON；
- LLM 不可用或输出异常时，使用规则 fallback 生成基础行程骨架。

输出字段：

- `daily_plan`
- `needs_replan`

### 5. 交通校验节点 `transport_validator`

职责：

- 遍历每天相邻景点；
- 调用 `route_planning` 查询交通；
- 将交通结果写入 `transport_segments`；
- 对步行距离过长、交通失败等问题写入 `validation_issues`；
- 必要时设置 `needs_replan=True`。

输出字段：

- `transport_segments`
- `validation_issues`
- `needs_replan`
- `replan_attempts`

### 6. 餐住推荐节点 `poi_enricher`

职责：

- 选取行程中最后一个可用景点作为周边搜索中心；
- 调用 `search_nearby_poi` 获取餐饮候选；
- 调用 `search_nearby_poi` 获取住宿候选；
- 将结果写入 `meal_options` 和 `hotel_options`。

输出字段：

- `meal_options`
- `hotel_options`
- `validation_issues`

### 7. 最终回复节点 `final_responder`

职责：

- 基于结构化状态生成最终 Markdown 回复；
- LLM 不可用时使用规则渲染 fallback；
- 把最终内容写入 `messages`。

输出字段：

- `messages`
- `final_status`

## 从 `new/` 迁移时的适配

`new/` 中的实现已迁移到正式入口，但做了以下适配：

1. 工具导入改为正式 `tools/`，不再依赖 `new/tools/`。
2. 读取第一阶段统一返回协议：
   - `web_search` 读取 `data.results`；
   - `get_location_coordinate` 读取 `data.locations`；
   - `search_nearby_poi` 读取 `data.pois`；
   - `route_planning` 读取 `data` 中的路线摘要。
3. 保留 `PublicState` 兼容名，避免旧代码导入立即失效。
4. `graph.create_graph(model_name, is_async=True)` 保留 `is_async` 参数，避免 `chat_service` 现有调用方式失效。
5. 阶段 LLM 调用集中到 `agents/stage_executor.py`，各节点只负责阶段逻辑。

## 验收标准

第三阶段完成后，应满足以下标准：

- `PublicState` 已升级为结构化状态；
- 状态包含 `selected_destination`、`user_constraints`、`attractions`、`daily_plan`、`transport_segments`、`meal_options`、`hotel_options`、`validation_issues`；
- 正式图包含意图识别、目的地澄清、景点采集、行程规划、交通校验、餐住推荐、最终回复节点；
- 工具结果能沉淀到结构化状态；
- 正式入口不再依赖单一大 Prompt + ToolNode 控制完整流程；
- 从 `new/` 迁移的实现不再依赖 `new/tools`；
- 原有工具层和 API 冒烟测试继续通过；
- 新增图结构测试通过。

## 风险与注意事项

1. 当前多节点实现仍是参考版，行程规划质量依赖阶段 Prompt 和 fallback 规则，后续仍需结合真实对话手动验收。
2. `/chat/stream` 接口结构未变，但工具调用不再通过统一 ToolNode，因此前端调试面板看到的工具事件可能不同，后续如果需要完整展示节点内工具调用，需要增加节点级事件或日志输出。
3. 目的地澄清节点当前在有候选时会默认选择一个候选继续流程，生产化版本可以改为停下等待用户确认。
4. 交通校验目前只做基础规则判断，例如步行距离过长；更复杂的开放时间、跨城交通和节奏校验可放到后续阶段。
5. `new/` 目录已在正式入口稳定并通过测试后删除，后续不再维护双版本实现。
